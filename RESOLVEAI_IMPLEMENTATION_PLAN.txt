# ResolveAI — Complete Implementation Plan for OpenCode

## PROJECT IDENTITY

You are building ResolveAI, a serious portfolio-grade Forward Deployed AI Engineer project.

ResolveAI is an AI-Powered Business Resolution Engine for a fictional B2B/e-commerce company called Northstar Commerce.

This is NOT a generic customer-support chatbot.

The system receives an operational request, investigates business data, retrieves relevant company policies, makes a recommendation, passes that recommendation through deterministic policy enforcement, executes authorized actions safely, requests human approval for high-risk actions, verifies outcomes, records an audit trail, and produces a grounded explanation.

The central workflow is:

REQUEST
→ UNDERSTAND
→ INVESTIGATE
→ RETRIEVE POLICY
→ DECIDE
→ POLICY CHECK
→ APPROVAL IF REQUIRED
→ EXECUTE
→ VERIFY
→ AUDIT
→ RESPOND

The project must demonstrate evidence that the developer understands Forward Deployed Engineering, AI systems architecture, agentic workflows, enterprise integrations, reliability, safety, evaluation, and measurable business outcomes.

# PART 06 — DETERMINISTIC POLICY ENGINE

## Objective

Build the deterministic business policy engine.

This is one of the project's most important FDE differentiators.

The LLM may recommend an action.

The deterministic policy engine decides:

ALLOW
DENY
REQUIRES_APPROVAL

The LLM must NEVER override policy decisions.

## Initial rules

Implement rules such as:

1. Refund <= $100 AND policy eligibility satisfied
   → ALLOW automatic execution

2. Refund > $100
   → REQUIRES_APPROVAL

3. Refund violating eligibility requirements
   → DENY

4. Cancellation after shipment
   → REQUIRES_APPROVAL or escalation according to defined business policy

5. Unknown/high-risk actions
   → REQUIRES_APPROVAL

## Policy engine requirements

Input should include relevant structured facts, for example:

- action type
- order status
- shipment status
- refund amount
- eligibility result
- policy evidence

Output should be structured:

{
  "decision": "ALLOW | DENY | REQUIRES_APPROVAL",
  "reason": "...",
  "policy_rule": "...",
  "risk_level": "LOW | MEDIUM | HIGH"
}

Keep rules deterministic and testable.

Do not ask Gemini to enforce policies.

Add comprehensive tests for:

- allowed refund
- approval-required refund
- denied refund
- cancellation after shipment
- unknown action

# PART 12 — IDEMPOTENCY, RETRIES & RELIABILITY

## Objective

Add production-oriented reliability controls.

## Idempotency

Critical side effects:

- issue_refund
- cancel_order
- future notification actions

Use operation_id.

Example:

refund-order-10482-74.99

Before execution:

Already executed?
→ Return previous result.

Not executed?
→ Execute.

Store operation state.

Prevent duplicate side effects on retries.

## Retries

Implement lightweight retries only for transient/read-safe operations.

Pattern:

attempt 1
→ failure
→ short backoff
→ attempt 2
→ failure
→ attempt 3
→ mark failed/escalate

Do NOT blindly retry dangerous side-effect operations.

Differentiate:

READ operations

from

SIDE-EFFECT operations.

## Timeouts

Add practical timeout boundaries around external/LLM/database operations where appropriate.

## Failure handling

Use structured errors.

Track retry counts.

Ensure workflows transition to FAILED safely when unrecoverable.

## Tests

Test:

- duplicate refund request
- transient read failure
- failed operation
- timeout handling
- side effect not duplicated

STOP after Part 12.
